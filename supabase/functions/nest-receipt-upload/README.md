# Nest receipt upload

This gated Edge entry point accepts `POST ?uploadId=<UUID>` with raw JPEG/PDF bytes, a user's bearer token, expected `X-Nest-Household` and the project's publishable `apikey`. It verifies the user through Auth, obtains current membership through caller RLS, rejects an old form targeting a different household, inspects bounded bytes, computes SHA-256 and reserves the exact identity. It never posts an expense. A successful response requires a caller-authorized download with matching digest, byte count and MIME, including after an uncertain write. No overwrite is allowed.

The only privileged request is an immutable Storage POST to the inspected, reserved path. Reads and reservations use the user's token. The added Storage trigger rechecks membership at native insertion; existing pending/claimed/cleanup guards remain in force. Errors return finite codes without provider messages or secrets. PDFs are signature-checked, not parsed or malware-scanned.

Deployment prerequisites (not performed): an explicitly selected isolated development project; reviewed identity/writer migrations plus their existing receipt/financial prerequisites; the private `household-files` bucket and audited policies; `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and explicit `NEST_SUPABASE_PUBLISHABLE_KEY` configured in the Edge environment. The general API and mobile app must never receive the service credential. Keep the user-JWT gateway check enabled and verify it with that project's signing configuration; the handler independently calls Auth and enforces membership. See Supabase's [user authentication guidance](https://supabase.com/docs/guides/functions/auth) and [authorization headers](https://supabase.com/docs/guides/functions/auth-headers), checked 21 September 2026.

Local verification uses TypeScript 7 for the shared package, pinned Deno 2.9.6 for the entry point, real JPEG decoding and disposable PostgreSQL/PostgREST. Simulated Storage responses test byte comparison and lost acknowledgments; the real HTTP integration deliberately asserts unavailable Storage returns failure. No hosted function deployment, real Storage upload/download or iPhone selection is claimed. The CI workflow checks the frozen Deno lockfile and never deploys or applies production migrations.
