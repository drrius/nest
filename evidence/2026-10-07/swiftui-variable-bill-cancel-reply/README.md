household, zero skips: prepare variable-only rule, attempt refused Save, cancel
pending entry, offline restart, recover cancellation/Continue, partner SDK read
and ordinary owned-rule cleanup. Four methods drive the shipping UI; three use the signed SDK for preparation,
partner reading and cleanup.

Every financial Save is blocked by the relay before reaching the backend. The
reviewed CHF0.02 input creates only a local uncertain intent. Native cancellation
then commits one backend tombstone, loses its reply and retains the original
operation/command with its cancellation flag. Actual restart discovers that entry
from Money without a live rule read. Its exact saved bytes remain unchanged.

Retry sends the same operation-only cancellation body and receives the original
cancelled outcome. [Request proof](request-proof.json) records two exact cancellation
POSTs and no forwarded financial Save. The UI shows Pending entry cancelled and
Continue clears the local terminal request, returning to the still-due bill form.
The partner SDK confirms an unconsumed rule and unchanged zero balances. Normal
rule cancellation removes the owned fixture from active use without posting money.

the legitimate cancellation retry. That failure remains in [results](results.json).
The corrected relay resumes only recovery; neither the original Save nor initial
cancellation tap is repeated. It allows one exact retry and still blocks all
financial Saves. This correction changes test transport, not shipping behavior.
