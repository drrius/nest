# App-wide Calendar permission recovery — 30 September 2026

Nest now checks Calendar access when a verified account becomes active or the app returns to the foreground, across all four tabs. Denied/restricted access journals an actor/household/environment-scoped removal intent **before** any network read. Losing connectivity before reading consent therefore retains the request. Restoring permission alone does not cancel this intent or enable sharing. Recovery runs on the next foreground entry or explicit Retry removal; there is no claim of a background worker or automatic connectivity monitoring.

The new SQLite intent is separate from an uncertain sharing change. Enable/publish and ordinary consent retries are fenced while removal is pending. An uncertain off write keeps its exact operation and baseline through restart. Only an authoritative stale-revision response permits rebasing another off request. A validated off receipt atomically clears the removal and any proven-superseded older change. Wrong receipts, another actor/household/lease, future revisions and storage failures do not authorize clearing intent. A pending enable at permission loss latches the need for a server off revision: its later acknowledgement cannot make an earlier disabled-state read safe. The server fence prevents both an unsent delayed enable and retry of an already-committed enable from turning sharing back on.

The root shows an honest pending-removal notice with Retry, without blocking household screens. Settings also expose retained removal, disable enabling without access, and clear an old read error only after a successful fresh read. Existing authorized server commands and the AI Calendar-settings handoff are reused; no new public API or EventKit write feature was added.
