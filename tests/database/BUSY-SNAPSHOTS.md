# Consent-bound busy snapshots

This is a gated additive M6 database boundary. It stores no event text, calendar identifiers, attendee data or locations. It has not been applied to production or connected to a device.

The native app keeps per-calendar selection locally. Every change to that selection calls `nest_set_calendar_consent`, even if at least one calendar remains selected. This increments the server consent version, invalidates all in-flight captures and atomically deletes the old aggregate snapshot. With no selected calendars, set `enabled=false`. Owner-only consent rows start disabled. A repeat of the most recent operation with identical input returns its version without clearing a newly published snapshot; stale operations after a later settings change conflict. A new settings intent needs a new operation UUID. The future UI must complete this online consent change before publishing from its new selection.

Before reading selected calendars, call `nest_begin_busy_capture` with the consent version. It issues a monotonically increasing generation and server start time. A newer capture supersedes an older generation. `nest_publish_busy` accepts only the current enabled consent/generation and stores a complete snapshot atomically. The same capture cannot later change its payload. Starting another capture retains the prior unexpired snapshot while fetching; a settings change removes it immediately.

The snapshot contains only covered epoch-millisecond bounds and at most 512 sorted, merged, disjoint `{start,end}` intervals, plus server freshness metadata and member/household identity. The server rejects extra keys rather than stripping personal data silently. Coverage is bounded to 31 days. Numeric bounds must be integer milliseconds. Capture freshness expires 15 minutes after the server-issued capture start, not publication time or device time; a delayed/retried response cannot renew it. No automatic background model usage or paid scheduling is introduced.

Partner RLS requires both members to remain in the household, enabled consent and an unexpired snapshot. Consent itself is owner-only. A missing/expired snapshot means **unknown**, never free. An empty valid snapshot only describes its covered range. Offline permission revocation cannot contact the server immediately; existing remote visibility is bounded by the 15-minute expiry, and the device must clear consent as soon as it reconnects. Physical-device lifecycle behavior remains unverified.

Membership removal cascades only these ephemeral consent/snapshot records, so rejoining cannot silently restore sharing. Financial history/approval audit records are unrelated. The foreign-key shape was audited against the legacy `20260809100000_core_tenancy.sql` at `4a528c96caf41515a70291ccecbba9d7b35e3349`. No existing data was read or deleted by these fixture tests.

Locally verified: 12 PostgreSQL tests cover opt-out/publication races, selection changes, stale generations, immutable retries, owner/partner/outsider access, private-field rejection, expiry, membership removal/rejoin, and rollback on snapshot replacement failure. Supabase security advisors against the disposable local Unix-socket fixture reported no issues. The cluster harness is deliberately reused unchanged from PR #4. These tests do not prove EventKit access, full Supabase schema compatibility, API payload mapping or two-device privacy.

Remaining: authenticated API/Effect commands and exact response schemas, per-calendar native consent UI/storage, device permission/capture lifecycle, integration with the sanitized reader in PR #7, partner/AI availability consumption, full-schema migration rehearsal and network inspection on two phones. No actual Calendar flow is complete from these RPCs alone.

Before presenting sharing controls, call `nest_get_calendar_consent`. It initializes disabled consent with a server-generated incarnation UUID. Bind the exact user intent, capture and publication to this identity. Membership deletion discards it, so delayed requests cannot revive sharing after rejoin even if numeric revisions repeat. Never automatically rebind an old intent to a fresh incarnation. The suite includes both delayed-opt-in and delayed-capture regression cases.
