# Durable native action approvals

The additive migration is gated and has only run in disposable synthetic PostgreSQL clusters. No production connection or data migration was used.

`nest_propose_action` binds the authenticated member and current household membership to a stable invocation, finite financial command name, command schema version and exact JSONB payload. Duplicate proposals return the same record and never extend the 15-minute expiry; changed content needs a new invocation and a new visible approval. Payload size is bounded to 64 KiB. These are proposal records, not valid financial entries: the eventual command still validates its own schema and business invariants.

`nest_decide_action` verifies that the owner is still a member and that the displayed invocation, command, version and payload match before deciding. Concurrent approve/deny requests serialize; a terminal decision cannot be changed. Expired records cannot be revived. Only the originating member can select a record through RLS. Membership revocation hides retained audit records and prevents further decisions/consumption. Membership rows are locked against deletion during the authorizing transaction; the tests verify post-revocation denial, not every possible revocation interleaving.

`private.nest_consume_action_approval` has no authenticated/anonymous EXECUTE grant or public RPC facade. A financial command must first check its existing operation receipt, then call this helper and perform its write plus receipt inside one transaction. The helper verifies current ownership/membership, household, invocation, command, schema version, exact payload, approval and expiry under a row lock. Failure rolls the approval consumption back. A second consumption fails; a retried successful command must return its stored receipt before attempting consumption again. Do not split consumption and the actual write across API calls.

Private helpers use an empty search path, fully qualified references and explicit identity checks. Public facades are security invoker. Approval records deliberately retain actor/household UUIDs without cascading membership foreign keys so revocation cannot delete authorization history. They contain no tokens or signing secrets. AI SDK approval responses alone never update these records or authorize a write.

Verified locally with PostgreSQL 18.6: nine database tests cover owner/partner/outsider/anonymous access, denied direct mutation/consumption, pending/denied/expired rejection, payload/version/invocation/command/household tampering, idempotent proposal/decision, rollback coupling, concurrent execution, competing decisions and revoked membership. The internal write fixture is intentionally a single synthetic row, not a ledger implementation or proof of financial invariants. The disposable-cluster runner is deliberately reused, unchanged, from the audited PR #4 test harness; it accepts only a server-binary directory, never an existing database URL.

Supabase CLI `db advisors --type security --fail-on error` against the disposable fixture's Unix socket returned **No issues found**. Its generic “Connecting to remote database” message referred to the explicit local socket URL. This does not replace advisors/RLS checks against a complete isolated Supabase schema before release.

Still required: authenticated API/UI proposal and decision flows, private conversation/invocation ownership, the production financial command/receipt transaction, current-record version checks, persisted chat approve/deny/resume, native approval cards and lost-response journeys. No milestone is complete from this migration alone.
