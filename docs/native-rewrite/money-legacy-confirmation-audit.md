# Retained draft confirmation audit

Reference repository: Household OS at `4a528c96caf41515a70291ccecbba9d7b35e3349`. Only local source and disposable synthetic data were used.

The final `public.confirm_expense_draft` in `20260812090000_notifications_realtime.sql` locks the original draft, accepts only pending rows, posts through the audited financial engine, marks the draft posted and retains its original fields. Its household-wide retry key has the same actor-binding limitation already documented for legacy expense commands. It accepts nullable overrides and substitutes old fields; Nest must instead bind complete explicitly reviewed expense terms and a fingerprint of the original draft. A posted draft's event is identified by the exact `financial_events.expense_draft_id` relationship, never by a description match.

`tests/database/legacy-money/draft-confirmation.sql` is the complete unchanged final function statement, with its source hash in the existing provenance manifest. It is installed only in a disposable race test against the new native transaction. No old server handler, generator or deployment configuration is copied. The draft-table fixture remains a deliberately limited audited column/constraint interface, not a full migration-chain rehearsal.

The native boundary reuses `private.post_financial_event` from the already audited `20260812202316_share_ledger_lock.sql` implementation and the current strict native expense validator. The transaction locks current members, the draft, the ledger and selected category before consuming exact private approval. It explicitly requests the ordinary `expense_posted` activity/partner notice from that engine; passing a null activity kind would suppress those side effects. It preserves original draft terms and writes only posted status, while the immutable financial event records the explicitly reviewed terms and original draft link. No recurring mandate, cycle, rule or future generation setting changes.

Actor/household/operation/payload-bound append-only receipts and cancellation fences replace the old household-wide retry identity. Direct Save and approval-required execution use the same transaction; approval, event, allocations, two zero-sum ledger entries, notice, draft status and receipt commit or roll back together. Existing event links, nonpending/shopping drafts and changed raw content are rejected. Receipt attachments and grocery totals are outside this retained recurring-draft command; they remain supported by existing ordinary expense flows. No existing attachment is removed or rewritten.

Native API/form/recovery, private AI proposal/card and full production migration rehearsal remain separate required integration work. The audit and database boundary are not a completed user flow or evidence of device behavior. Production application remains gated.
