# Settlement engine audit

Source: Household OS commit `4a528c96caf41515a70291ccecbba9d7b35e3349`. The complete final `20260812201042_atomic_settlement.sql` migration is retained in `tests/database/legacy-money/settlement-command.sql`, with its exact SHA-256 in `provenance.json`. No legacy screen or cookie-bound service was copied. This audit uses disposable synthetic PostgreSQL only.

The audited transaction authorizes a current member of an exactly two-member household, binds a legacy request receipt, and takes the same `ledger:<household>` advisory lock used by the final expense posting engine. It derives the debtor and outstanding receivable from retained ledger entries. A partial amount must be positive and no greater than the current outstanding amount; the named payer must be the debtor. The real posting engine appends one settlement event, two zero-sum ledger deltas, activity and partner notification/outbox work in the same transaction. Settlements do not allocate a new shared expense. No bank transfer is performed.

Two legacy behaviors need a stricter Nest boundary. The old receipt identity is household-wide rather than actor-bound, so another member can replay the same key and payload. Nest must authorize before replay and bind actor, household, operation and exact payload, using an unpredictable internal legacy key after its own receipt lookup. More importantly, legacy `full` mode ignores the supplied amount and derives a new amount from the live ledger. A test supplies one centime and observes the whole 701-centime balance posted. Native and AI confirmation must bind the displayed exact amount and debtor; a changed full-settlement balance must return a conflict requiring a new review, rather than silently increasing what was approved. Acquire the shared ledger lock before that validation and call the audited engine with the already validated exact amount. Consume an AI approval, post and record the Nest receipt atomically. Ordinary native Save can authorize the displayed transaction directly.

The five database cases cover partial followed by full settlement, wrong payer/outsider/anonymous/overpayment denial, immutable history, eight concurrent identical retries, distinct full-settlement races, actual notification failure rollback and successful same-key recovery. Sixty-four generated partial/full sequences reach the safe-integer centime endpoint and verify zero balances, two zero-sum entries per event and preservation of original expense amounts against their retained receipts. The first run contained an invalid test-only `event_type` column assertion; it was replaced with a check against the actual receipt payload and retained event schema, and the complete suite passed.

This proves the selected legacy engine behavior and identifies its adaptation requirements. Nest settlement contracts, exact approval enforcement, API/AI commands, native full/partial entry, response-loss recovery and physical-device interaction remain unfinished. No production migration, data change or deployment is authorized by this audit.
