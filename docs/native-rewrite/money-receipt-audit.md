# Receipt attachment audit

Reference: Household OS commit `4a528c96caf41515a70291ccecbba9d7b35e3349`, migration `20260904224746_household_attachments.sql`. The complete registry, reservation, claim, cleanup and Storage-policy statements are pinned unchanged in `tests/database/legacy-money/receipt-attachments.sql`, with a SHA-256 provenance entry. Only unrelated shopping-session and chore-completion trigger declarations are omitted. This is a disposable audit fixture, not a production migration.

The private `household-files` bucket retains existing paths. Reservation binds a path and MIME type to the uploader. Only the inspected privileged writer can insert; ordinary authenticated callers have no insertion or overwrite policy. Financial insertion claims an existing object under the registry row lock. A claimed attachment stays claimed after reversal/replacement. Cleanup acquires the same lock, transitions unclaimed uploads to deleting, and leaves a deleted tombstone after object removal. This prevents a delayed privileged upload from resurrecting a removed file or deleting a receipt as it becomes linked to an expense.

Five focused PostgreSQL cases pass, including twelve concurrent claim/cleanup races, wrong uploader/tenant/anonymous denial, direct insertion and overwrite denial, wrong MIME rejection, lost-upload acknowledgment, retained receipt references through correction, failed foreign/missing receipt rollback, interrupted cleanup and tombstones. The fixture models only the Supabase-owned Storage metadata interface; application SQL and the financial engine are real pinned statements. It does not emulate object bytes, the Storage API's metadata-deletion guard, signing/download, or the deployed Edge Function. Direct metadata deletion in these synthetic tests is not an implementation approach.

## Native integration requirements

- Expose receipt operations through strict authorized commands scoped to the current household. Preserve existing identifiers and paths. Do not migrate files or change production bucket/policies as part of implementation.
- New native paths must be canonical lowercase and receipt-only. The legacy reservation allows uppercase path components while its read policy compares the household prefix case-sensitively; do not create such unreadable paths.
- Use immutable upload identities and bounded bytes. The existing reservation recovers by path, not content digest: reusing an upload ID with different bytes can return the original object. Preserve the selected file/identity across an explicit retry, and never report that changed bytes replaced an existing object.
- Audit the actual byte-inspecting Edge implementation before reusing it. Its current entry point accepts fully decoded bounded JPEG or PDF-signature inputs, not every image MIME listed by the bucket. Device selection must normalize supported photos and report unsupported/oversized files honestly. Do not send service credentials to native code or the general API client.
- Claim the receipt in the same transaction as an expense. Include the exact receipt reference in idempotency and AI approval bindings. A file upload alone must never record money. Corrections retain the original receipt unless a separately reviewed replacement policy is explicitly implemented.
- No model tool may select arbitrary device files or approve a financial mutation. Provide an honest native device handoff for selecting/uploading a receipt. Do not send receipt bytes or signed URLs to a model by default.
- Serve retained receipt access only after current membership checks. Avoid public URLs, cross-account caching and unbounded signed-link lifetimes. Account replacement must hide receipt content and cancel loading.
- Use the Storage API for real uploads/downloads/deletions; do not mutate Storage metadata directly. Claimed financial attachments must remain retained. Uncertain upload/cleanup outcomes need explicit reconciliation before retry or abandonment.

Current [Storage access-control documentation](https://supabase.com/docs/guides/storage/security/access-control) confirms the distinct insert/select/update permissions and service-key bypass. The [Storage schema documentation](https://supabase.com/docs/guides/storage/schema/design) requires API operations for actual objects. The official changelog was checked on 21 September 2026. Native transport, file selection/preview, complete upload/download integration and physical-device verification remain work to implement; this audit does not mark optional receipts complete.
