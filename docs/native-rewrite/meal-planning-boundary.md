# Private meal-planning boundary

The approved brief authorizes a planning service to use both members' dietary constraints. It does not authorize a partner-facing profile read, a raw planning-context chat tool, or disclosure of the other member's calorie goal. Missing food setup is unknown; generation must require both profiles before treating any restriction list as complete.

The new read-only context RPC is executable only by `service_role`. It uses invoker privileges with explicit SELECT grants, an empty search path, current requesting membership and exactly two household members. Authenticated and anonymous callers cannot invoke either its public wrapper or private implementation. Existing owner-only food-profile RLS is unchanged. The server verifies the bearer identity and selected household with its publishable-key path before using its separate redacted secret for the fixed context endpoint. It never accepts an actor/household from generation text. A database membership check repeats authorization at the privileged read.

The context carries both current members' restrictions, dislikes and portions; only the requesting actor's optional calorie goal; shared cooking preferences; and a stable state fingerprint. No personal event details, chat, memory, profile names or partner calorie target is returned. The opaque fingerprint covers profile contents/revisions and membership join identities as well as cooking choices, so later proposal approval can detect changed constraints or rejoined membership. Epoch timestamps make it independent of connection timezone. Missing profiles/preferences remain null rather than fabricated defaults.

This module is internal to `apps/api`: it is not registered in the API route table, assistant tool registry or client contract exports. Its returned context must stay inside generation and constraint validation. Future proposal responses contain only visible meal content and approval metadata. The service must recheck current constraints at approval; a stored hash alone does not enforce that until the proposal transaction is implemented.

Supabase documents secret keys as backend-only credentials mapped to the RLS-bypassing service role; they are not user authentication. The implementation keeps these two checks separate and disables redirects for both credential paths. `apikey` joins Effect's configured redacted header names. No live key was fetched or installed.
