# Private meal-planning boundary

The approved brief authorizes a planning service to use both members' dietary constraints. It does not authorize a partner-facing profile read, a raw planning-context chat tool, or disclosure of the other member's calorie goal. Missing food setup is unknown; generation must require both profiles before treating any restriction list as complete.

The new read-only context RPC is executable only by `service_role`. It uses invoker privileges with explicit SELECT grants, an empty search path, current requesting membership and exactly two household members. Authenticated and anonymous callers cannot invoke either its public wrapper or private implementation. Existing owner-only food-profile RLS is unchanged. The server verifies the bearer identity and selected household with its publishable-key path before using its separate redacted secret for the fixed context endpoint. It never accepts an actor/household from generation text. A database membership check repeats authorization at the privileged read.

The context carries both current members' restrictions, dislikes and portions; only the requesting actor's optional calorie goal; shared cooking preferences; and a stable state fingerprint. No personal event details, chat, memory, profile names or partner calorie target is returned. The opaque fingerprint covers profile contents/revisions and membership join identities as well as cooking choices, so later proposal approval can detect changed constraints or rejoined membership. Epoch timestamps make it independent of connection timezone. Missing profiles/preferences remain null rather than fabricated defaults.

This module is internal to `apps/api`: it is not registered in the API route table, assistant tool registry or client contract exports. Its returned context must stay inside generation and constraint validation. Future proposal responses contain only visible meal content and approval metadata. The service must recheck current constraints at approval; a stored hash alone does not enforce that until the proposal transaction is implemented.

Supabase documents secret keys as backend-only credentials mapped to the RLS-bypassing service role; they are not user authentication. The implementation keeps these two checks separate and disables redirects for both credential paths. `apikey` joins Effect's configured redacted header names. No live key was fetched or installed. ## Proposal contracts and intended persistence

A private proposal has generating, ready, failed, approved or discarded state. Generating/failed records have no pretend meal content; failed records carry a finite safe reason. Ready/approved content contains distinct dated slots in one Monday–Sunday week. Each entry retains either a saved recipe with its library revision or a complete suggested recipe. Familiar-only content cannot contain new suggestions. Optional per-serving calories are estimates; no personal goal, food-profile payload or constraint fingerprint belongs in the public proposal envelope.

Generation and single-slot change inputs cannot grant approval or supply an actor, household, retry identity or arbitrary replacement week. Explicit native approval identifies an exact proposal revision. Approval receipts bind the approved revision, resulting proposal revision, original/resulting meal-week revisions and distinct inserted entry identities. The intended approval transaction inserts only proposed empty slots, preserves existing occupied slots and creates neither groceries nor preparation. Ingredient review remains a separate confirmation. These codecs do not enforce authorization or execute approval by themselves.

Suggested recipes must be retained with the approved meal without silently adding an active saved-library recipe. The planned-recipe decoder now accepts a complete one-off recipe with `definitionId: null` and `libraryRevision: null`; saved definitions retain their original nonnull identity and library revision. One-off reads require servings, instructions and ingredients, and both variants share ingredient ordering/identity checks. The additive storage candidate permits null provenance without granting writes. Existing detail reads, cached snapshots and leftovers preserve it without changing the library. Approval still needs to create these snapshots atomically. Generation receipts describe the immutable start, while current private reads distinguish pending/failure/completion after interruption. Private worker storage, recovery and generation-time constraint/expiry checks are implemented. Approval-time checks, exact native confirmation and matching assistant actions still need implementation and verification.

## Reader compatibility gate

Existing saved-library records and response shapes are unchanged. The new nullable-provenance variant extends the unreleased version-1 planned-detail contract. Older decoders reject that new variant rather than misidentifying it as a library recipe. No released native binary or production one-off snapshot is claimed; deployment must establish compatible native readers before enabling the future proposal writer. Do not activate generation or approval against an older client as part of applying this additive migration. Existing records are not rewritten, and no migration adds meals or groceries.

## Bounded structured generation

The internal orchestrator consumes already-authorized current context, week, a bounded shortlist of up to fifty saved recipe details at one revision, and sanitized busy snapshots. It checks household/member bindings, freezes its input, and derives exactly the configured empty slots. The authenticated generation route reserves a private idempotent operation and reads current authorization, library and calendar sharing before obtaining a single worker claim. This internal model function alone supplies none of those persistence guarantees. Large inputs fail rather than silently omitting dietary constraints. Unknown/incomplete food setup is not equivalent to an empty restriction list.

The first SDK call returns only saved definition choices or complete new recipe suggestions. The server substitutes canonical saved content and rejects unknown definitions, incomplete legacy recipes, invented slots and familiar-only violations. No new suggestion can invent a source URL or grocery category identity. Both member constraints, portions and cooking preferences guide generation; only the requesting member's optional calorie target is available, and the prompt forbids disclosing profiles or goals in recipe text. Names, member/household identities, the state fingerprint and calendar event metadata are never sent. The second call separately reviews the exact resolved recipes against the dietary/cooking constraints and must cover every slot explicitly as safe. It does not see the personal calorie target, rewrite content or authorize any action.

Each stage has no tools, no automatic provider retries, a 30-second SDK timeout, a 16,384-output-token ceiling and a 128-KiB UTF-8 input ceiling. Provider errors/raw output are replaced with finite failures; cancellation reaches the active call. The total two-call hosted latency and configured model spend need validation before enabling a production route. A timeout is a failed proposal attempt, not permission to regenerate an already committed operation blindly. Reservation, one-time worker claiming and owner recovery are now persisted separately from provider calls.

Schema and simulated-model checks prove data binding, conservative failure handling and privacy projection; they do not prove semantic dietary safety or absence of prompt injection in a real model. Live provider tests must establish schema compatibility and representative restriction handling. Production enablement remains blocked on those checks, authorized provider configuration and the complete proposal/approval lifecycle.

## Private reservation storage

A gated additive migration stores proposal metadata/content and immutable start/discard receipts in `private`, with RLS enabled and no direct client or service-role grants. Narrow invoker public wrappers call private definer commands that derive the actor from authentication and recheck current membership. Reads return only the owning actor's public proposal envelope; partner access never inherits ownership. Internal projection helpers have no client execute privilege, and the constraint fingerprint remains private.

Starting reserves a UUID at revision 1 without posting a meal. It requires complete two-person food/cooking setup, an exact week baseline and at least one configured empty slot. Operation replay returns its immutable original start receipt even after later profile changes or discard, but always rechecks membership first. Discard similarly binds the exact current revision, rejects approved/already-discarded states and retains any existing visible content. Receipt insertion and state transition share one transaction; failures roll back both. Write commands require read-committed isolation.

The record carries a 24-hour deadline to accommodate a planning session without retaining an indefinitely actionable proposal. The worker migration enforces expiry during claim/completion/recovery and adds a two-minute claimed-worker deadline. Only service-role wrappers can claim or complete, and direct table access remains revoked. Completion compares current constraints, exact saved recipes and every empty configured slot before storing a ready preview. Identical completion retries return their historical result; separate owner reads return current state. Interrupted workers fail once and cannot be automatically claimed again. Exact approval, native/assistant wiring and grocery review remain unfinished; generation never posts active meals.

## Authenticated generation and recovery API

`POST /v1/meals/proposal/generate` accepts only the strict native generation input. Identity and household selection are verified before any user-scoped or privileged read. Start receipts are immutable; retries first recover current proposal state. Ready, failed or discarded proposals do not call the model again. The response binds the receipt to the current actor-private envelope and never includes the worker capability or raw planning context.

Fresh inputs include the active week, internal constraint projection, visible sanitized busy snapshots and the first library page (at most fifty recipes, four concurrent detail reads, one exact library revision). Only complete recipes enter the shortlist; this is not an exhaustive search of a larger library. Input loading has a thirty-second aggregate deadline. The worker claim is acquired only after loading, and its fingerprint/week baseline must match before provider dispatch. SDK stages run under the remaining worker deadline. Finite failures are persisted; cancellation leaves a claimed job for explicit recovery rather than making an unobserved background model call. Lost claim acknowledgment never authorizes a retry to generate. Lost completion acknowledgment is recovered from the recorded proposal without a second provider run.

`GET /v1/meals/proposal?proposalId=…`, `POST /v1/meals/proposal/recover` and `POST /v1/meals/proposal/discard` use the caller's token and remain available without model credentials. Recovery terminalizes expired unfinished work; it does not generate. Discard requires the exact displayed revision and stable operation UUID. Unknown/duplicate query fields and injected identity/approval fields are rejected. All responses are private/no-store. The generated preview remains separate from the active week until the still-unimplemented explicit approval transaction.

Development generation requires both an explicitly configured Gateway model and `NEST_SUPABASE_PLANNING_SECRET`, held as a redacted server-only value. Neither is configured automatically; startup performs no migrations. A missing model or secret returns unavailable for generation while history/recovery/discard remain usable. Current tests run the actual Effect HTTP adapters, AI SDK, PostgREST and PostgreSQL with synthetic Auth/key translation and simulated provider responses. Hosted credentials, latency/quotas, semantic dietary safety, native interaction and production enablement remain unverified and separately gated.

## Native reservation and interruption recovery

`POST /v1/meals/proposal/reserve` exposes only the existing authorized reservation command and immutable start receipt. It never claims a worker or invokes a model. The native screen first persists its exact generation input in account/lease-scoped SQLite metadata, reserves the proposal, persists the returned ID, and only then explicitly requests generation. A failed metadata write or account-lease change prevents model dispatch. A lost reservation response can be retried safely; a definite reservation conflict requires a fresh week/setup review.

Opening a week with stored metadata only reads/reconciles it. Continuing is explicit, and the server claim still prevents duplicate generation. No request enters the grocery/chore offline queue or runs on background synchronization. Stored metadata contains the generation input, proposal ID and any exact discard request; it contains no recipes, food profile, calorie goal, model credential or raw context. The online-only preview is discarded from memory when its runtime/account closes. Recipe and ingredient lists are virtualized, and a native discard alert binds the displayed revision. A newer local operation clears the older preview before applying its state. Terminal states must be confirmed before a new attempt replaces the metadata.

The ordinary native HTTP client keeps its fifteen-second deadline. Only the proposal generation call gets a 180-second client bound to cover authorization, bounded input reads and the two model stages. Leaving aborts the request; reopening reconciles the server's current state rather than assuming success. Native interaction/accessibility has not been device-tested, and approval/replacement/ingredient review remain unfinished.
