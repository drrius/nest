# Recurring Money audit

The approved native brief requires fixed automatic obligations after explicit mandate approval, variable bills awaiting entry/confirmation, immutable financial history, server scheduling and exactly-once cycles. Existing rules remain draft-only until individually opted in. An obligation is not proof of a bank transfer.

Selected Household OS sources are pinned by commit and SHA-256 in `money-recurring-provenance.json`. The source files were read without changing the legacy repository. The legacy pure recurrence module and its four meaningful examples establish weekly ISO weekdays, monthly day-of-month clamping, strict next-date semantics and inclusive windows. Nest reuses those semantics and examples, using the already audited UTC date helpers from its domain package instead of copying another date implementation. No legacy screen, scheduler or automatic posting behavior was copied.

The original date validator uses `Date.UTC` and rejects years 0001–0099 because JavaScript maps those years to 1901–1999. The original due-date loop is unbounded and computes a successor even after reaching the upper supported date boundary. Nest's pure planner supports validated years 0001–9999, returns null at exhaustion, bounds each catch-up page to at most 100 dates and returns the first unreturned due date as its continuation. The caller must preserve the exact schedule and window when continuing. This is planning only; it provides no permission to post or backfill history.

The legacy database generator locks active rules, inserts `expense_drafts`, deduplicates on `(recurring_expense_rule_id, occurred_on)` and advances `next_occurrence_on`. It does not post an approved automatic expense. The later version trigger updates `updated_at` on every mutation, including generation and pause/resume. Reusing that timestamp as an automatic mandate approval version would mix execution cursor changes with authorization changes. Native rule configuration revisions and execution state must be separate.

## Native implementation constraints

- Keep financial posting transactional with the ledger and a durable cycle receipt. Rule locks serialize posting, changes and pause/cancel. Replays return the original result rather than generating new obligations.
- Bind approval to the exact configuration revision, amount, payer, allocation, cadence and activation date. Cursor advancement must not change that configuration revision. Store authorizer separately from job executor.
- Activation begins prospectively unless backfill is explicitly approved. Catch-up covers missed approved periods only. Pausing preserves history and prevents future execution; resuming must disclose its first eligible cycle.
- A cycle must survive amount/payer/split edits and cannot be recreated by moving the due weekday/day. Use the civil weekly period (Monday through Sunday) or monthly period as its stable period identity, plus rule identity; retain period coverage when cadence changes so the first new period cannot overlap an already posted old period. Cadence changes must disclose the resulting first eligible due date. The forthcoming transactional schema must prove this across edits and retries rather than relying on a due-date-only unique constraint.
- Variable confirmation and fixed automatic execution share the same cycle claim. Explicit manual-entry linkage consumes that cycle; descriptions must never be used to infer a match. Corrections/refunds do not silently reopen a consumed cycle.
- Legacy rules and pending drafts remain separate from native automatic cycle authority. Migration cannot manufacture approval or automatically backfill them.

Current evidence covers pure date planning and private PostgreSQL planning parity, including stable civil periods and prospective coverage across cadence changes. The gated SQL helpers are immutable invokers without caller execution grants; they neither claim a cycle nor post money. Real PostgreSQL tests compare 1,500 generated plans with the domain implementation and cover early/terminal years and malformed inputs.

Native mandate setup/edit commands now retain immutable authorized configurations independently of execution state. Fixed mode binds exact centimes and allocations. Variable mode deliberately retains no amount/split authority: both are supplied and confirmed when that bill is recorded. Active overdue cycles must be resolved before editing the rule, so an edit cannot silently discard outstanding approved cycles by advancing the cursor. All setup/edits are prospective; historical backfill is not exposed. The first due date is part of the exact approved input and is rechecked against current coverage, including after concurrent execution. Tests prove direct/AI command authorization, revision conflicts, retries and rollback; they do not prove a scheduler or native screen.

Native configuration/confirmation and private AI proposal handoffs are implemented with local and CI evidence in the progress log. A private fixed-cycle transaction now atomically posts the exact mandate, stores its consumed civil-period receipt and advances coverage; scheduled posting remains inactive without a worker entry point. Pause/cancel commands preserve coverage and append labeled authorization revisions, so captured setup approvals and worker revisions become stale. Native lifecycle/resumption and variable-cycle confirmation, including private AI proposals, are now locally implemented and merged after review/CI. Controlled jobs, complete manual linkage, device acceptance and legacy migration reconciliation remain unfinished. The broader legacy scheduler/command statements have been inspected for these constraints, not certified or copied as working native infrastructure.

Prospective resumption preserves the paused configuration and consumed coverage, but grants a fresh authorization revision to the confirming current member. Its reviewed `resumeFrom` must be at least the server's Zurich date and the original start date; the exact first uncovered cycle is recalculated under the rule/cursor lock. The native preview defaults to the later of those two dates. The first resumed cycle and resume date are retained in append-only history. Paused backlog is skipped, never automatically posted or marked as a separately consumed cycle. Variable resumption still authorizes no amount/split. Resume shares the existing state operation lock/receipt and direct-request abandonment fence, while its distinct input/receipt schema prevents an old stop-only client from silently interpreting it as cancellation. Native/AI resumption adapters and explicit review are implemented; device/provider verification remains separate.

Manual linkage is an explicit choice of one existing, unreversed expense or expense replacement in the due cycle’s civil period. It never matches descriptions, changes the original event, posts another expense or changes the future mandate. It supports fixed and variable rules: the selected expense may have a different amount/payer/split from a fixed mandate, so native/AI review must show both the retained expense and the mandate and explicitly authorize consuming only this period. This is neither an inferred match nor a mandate edit. One event can satisfy only one cycle globally; already linked, reversed, foreign or out-of-period entries are ineligible. Corrections/refunds after linking retain the immutable consumed period. Source row locks precede the ledger lock, matching the existing correction/refund commands; rule and cursor locks still serialize cycle posting and state changes. Immutable receipts retain the financial snapshot as it was reviewed, even after subsequent corrections. Native linkage review/AI and scheduled execution remain future increments.

## Controlled worker boundary

The server-only worker primitives scan at most 100 current fixed/active due candidates in `(due date, household ID, rule ID)` order. Household identity is part of pagination because rule IDs are unique only within a household. Each execution is a separate transaction using the exact scanned household, rule revision and due date; no caller can override the server's current date or the retained authorization start/cursor. The existing cycle transaction rechecks the mandate, roster, authorizer, category and shared consumed-cycle identity, then commits ledger/cycle/cursor with an immutable job receipt. Job identity reuse with changed input fails. Different jobs may recover the same cycle receipt without posting twice; job records represent executions/recoveries, not a claim that each job created a new event. The retained mandate authorizer stays separate from the service worker identity.

Catch-up means repeatedly following an already authorized cursor after downtime. It never rewinds before setup/resume or infers historical opt-in. Candidate scans are advisory; changes during paging are rechecked by execution and newly eligible earlier candidates wait for a subsequent scan. The forthcoming runner must bound pages/attempts, preserve continuation past failures, reconcile retries and report failures rather than letting one bad mandate starve later candidates. Scanning does not acquire ledger locks. Posting a batch in one database transaction is deliberately excluded because holding one household's ledger lock while acquiring another rule can invert native command lock ordering. No hosted schedule is registered or active; deployment and activation require separate authorization and environment verification.
