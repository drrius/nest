# Two-action SQLite journal

This repository accepts only `chore.complete` and `groceries.setChecked`. Both operations are connected to native controllers, authenticated APIs and transactional server receipts. `OfflineStore` exposes typed Effect operations; SQLite's Promise transaction callback is contained below that service boundary. `expoDatabase` adapts the SDK 57 exclusive transaction API. The connection and authenticated session lifecycle belong to the application runtime.

An authorized session supplies its actor/household and a fresh random lease UUID on every activation. These local identifiers are cache isolation, never server authorization. Every transaction checks the current lease. Suspension invalidates existing callbacks without deleting pending work. Another account sees only its own rows; switching back can recover the original queue. Before offering destructive local cleanup, the UI must explain pending work and obtain explicit discard. No credentials or private chat content belong in this database.

A snapshot stores canonical versions and checked/completed state. A durable operation stores the local intent; reads overlay pending intents on existing snapshot rows. There is no separate optimistic state to lose between writes. Snapshot removal preserves the pending intent for explanation without recreating the item in the visible list.

`prepare` materializes and persists the exact wire command before network dispatch. Later attempts return that payload unchanged. Per-target successor operations wait for their predecessor's receipt and use its canonical version, including compatible no-op responses. Receipts update canonical state and acknowledgment in one transaction. A conflict remains recorded and blocks dependent operations; unrelated targets can continue. Device timestamps never decide ordering.

The caller must serialize its replay loop, pause when authentication expires, send the original operation identity through a server command with atomic receipts, map typed conflicts, and refresh a bounded authoritative snapshot after replay. Concurrent duplicate dispatch remains possible after interruption; only the server receipt protocol can guarantee exactly-once side effects. This journal deliberately does not claim that guarantee on its own.

Chore/grocery snapshots, cold-start identity recovery and account-level reconnect are implemented. Actual Expo SQLite execution, iOS file-protection verification and two-device fault journeys remain outstanding. The Node adapter executes the same SQL against file-backed SQLite and reopens it; this is not an iPhone process-kill test.

## Local journal bounds

Each actor/household may enqueue at most 1,000 unresolved operations (pending plus conflict). A duplicate retained operation stays idempotent at capacity; a new operation fails atomically with a clear native message. No successful check/completion is shown for the rejected intent. Connect and replay, or explicitly resolve known conflicts, to regain capacity. An existing queue above the limit is preserved in full on upgrade and can drain normally; capacity never silently discards work.

On account activation and successful acknowledgment, retain the most recent 1,000 acknowledged operations plus every older direct predecessor needed by an unresolved operation. Cleanup shares the lease/acknowledgment transaction; failure rolls back both cleanup and the surrounding change. A partial predecessor index keeps the dependency lookup bounded by unresolved work. Other accounts, snapshots, pending/conflicted rows and frozen wire payloads remain untouched. With a normally bounded queue this caps retained acknowledged rows at 2,000 and total journal rows at 3,000 per account; upgraded oversized queues are the explicit exception until drained.

Old acknowledged ancestry outside that window may disappear. An old UI intent with no retained proof of a compatible check sequence keeps its original expected version and conflicts if the server changed; cleanup never guesses a rebase. Pending children retain their direct parent's canonical receipt version and exact frozen wire across restart. Local receipt pruning does not change server idempotency history or financial history. Controllers generate fresh operation UUIDs for new intents; retained uncertain operations always reuse the original UUID.

`saveChores` preserves other item kinds; cached empty is distinct from never loaded. A rejected conflict and its dependent local intents can be explicitly discarded, while an uncertain pending command cannot be discarded through that API. Native transactions are serialized and drained before closing the connection; session leases still reject stale callbacks.

The root native `OfflineProvider` owns a single SQLite connection and account lease across household screens. Consumers release their controllers, not the shared lease. Account changes serialize open/initialize/activate/suspend/close operations; an old delayed open cannot replace a new identity. A failed close blocks replacement until retry succeeds. Six file-backed ownership tests cover restart, delayed open/activation, close/initialization failures, account isolation and setup/cleanup races. These test the lifecycle service through Node SQLite, not React Native mounts or Expo SQLite internals.

Money cache stores read-only balance, first history page plus 19 continuation pages, and up to 50 event details per actor/household. Saved time is a local stale-view label, not a server revision. It never stores receipt paths/content or financial commands. Account leases guard every read/save/clear; cancellation checks surround the transaction so stale request generations cannot replace the saved view. Native runtime integration must clear on access denial and distinguish cached/missing/failed reads.
