# Device calendar privacy boundary

`expoCalendarPort` uses the Expo SDK 57 Calendar API (`getCalendarPermissions(false)`, `getCalendars(EVENT)`, `listEvents`). iOS requires full calendar permission to read events; this adapter exposes no event or reminder writes. The config plugin includes an explanation of reading and opt-in busy sharing and omits Reminders usage descriptions. Expo config introspection verified those generated keys locally. The native full-access prompt, denial and grant paths were tested on isolated simulators. With permission granted on a fresh simulator, Nest read one fictional event created in the local iOS Calendar and displayed its title and time only in the personal agenda, including after a process restart. Busy sharing remained off. Physical-calendar privacy and partner publication remain unverified.

`CalendarReader` is the Effect service boundary. Permission requests are explicit and separate from reads. Captures check full-read permission before and after fetching only selected calendars. An absent selected calendar, revocation or fetch failure yields unknown availability. No sharing selection means disabled, not free. Local picker metadata is separate from the projection; it must not be published to partner or AI services.

`projectBusy` returns only a schema version, capture time, covered interval and merged UTC intervals. It never spreads input events or exports identifiers, names, locations, URLs, notes, attendees, calendar titles or recurrence metadata. Free/canceled occurrences are excluded; tentative, unavailable and unsupported availability conservatively block time. EventKit supplies expanded occurrences and detached exceptions. The projection does not expand recurrence rules again. Native absolute all-day bounds are preserved, including 23/25-hour DST days; ambiguous date-only/floating strings invalidate the capture rather than implying free time.

Queries are bounded to 31 days. Freshness is explicit at consumption through `availabilityFor(snapshot, query, now, maxAge)`; stale, future-dated or out-of-coverage data is unknown. The application/server must select and document the freshness policy. Unknown availability cannot justify an AI claim that either member is free. Busy results support warnings, never blocking household actions.

Verified: 10 examples/service fixtures plus 1,000 deterministic property cases for exact busy union, clipping, disjoint intervals, input reordering and duplicate occurrences. A development-build simulator verified native full-access permission and one ordinary local EventKit event read. Recurrence expansion, restricted calendars and all-day conversion still need native checks; physical-calendar behavior remains unverified. Expo Calendar 57 is not supported in Expo Go ([SDK 57 reference](https://docs.expo.dev/versions/v57.0.0/sdk/calendar/)).

Implemented in source: an authenticated consent/capture/publication API; account-leased SQLite calendar selections and exact unresolved consent requests; native per-calendar opt-in and stop-sharing controls; an account-bound publisher with foreground/reconnect refresh and a five-minute foreground timer. Cold restart never automatically retries an unresolved opt-in. Local IDs and titles never enter published payloads. A changed consent incarnation/version discards this device's stale selection. Permission revocation or a missing selected calendar stages an explicit disabled request; a lost response remains retryable and blocks further publishing.

Operational choice: the first publisher uses the existing SQL bound of the next 31 days and a 15-minute snapshot lifetime, conservatively shorter than the audit's initial suggested eight-week/24-hour defaults. Refresh runs only while active; no guaranteed background execution is claimed. Failed reads mean unknown availability, and declined events are excluded only when EventKit marks the current user as declined. Event/attendee metadata is projected locally and discarded. Read operations time out rather than hanging settings.

Still required for M6: end-to-end consent-bound publication and revocation, two-device privacy inspection, native recurrence/DST behavior and restricted work calendars, and owner-phone acceptance. Personal agenda and partner availability presentation are implemented; the simulator verified an ordinary local event read but has not verified partner publishing. Native-client/HTTP/PostgREST tests and an iOS export are not device verification.

## Personal agenda read boundary

`expoAgendaPort` and `makeAgendaReader` are separate from availability publication. The native adapter copies only local event identity, title, location, notes, bounds, all-day and status; it does not call attendee APIs or expose EventKit writes. The Effect reader checks permission and selected-calendar presence before/after fetching. Queries use the existing maximum 31-day bound; empty display selection returns no events without reading calendars. Errors contain finite reasons, never upstream personal text. Runtime/account ownership and view selection are wired through the account-leased Calendar tab.

`projectAgenda` preserves exact occurrence bounds, including 23/25-hour DST days and multi-day events; zero-duration events belong to the half-open query containing their start. Cancelled/unselected occurrences are excluded, while free events remain visible personally. Repeated native occurrences are deduplicated by local calendar/event/start identity; differing content under the same key fails honestly. EventKit expands recurrence; Nest does not expand it again. No projected event details are cached, uploaded or passed to AI.

The installed `expo-calendar` SDK 57 `ios/Next/CalendarNextModule.swift` getters return optional `event?.title` / `event?.notes`, despite non-null TypeScript declarations. Null display text is accepted without inventing content. Invalid/floating date bounds yield unavailable rather than a misleading empty agenda. A later simulator smoke verified one ordinary local event read; more complex EventKit behavior and physical-device acceptance remain open.

## Native personal agenda

The Calendar tab uses the account-leased agenda selection, local EventKit reader and `AgendaRuntime`. Native display switches save only local IDs before refreshing. They do not modify sharing selections or consent. Runtime reads check the SQLite lease before and after device access, and failures clear event rows without presenting unavailable data as an empty agenda. Failed selection saves retain the previous choice. Focus/foreground activates reads; blur/background/disposal clears private rows, selection metadata and calendar titles and cancels stale work. Foreground minute refreshes recheck access. Lifecycle transitions are verified with controlled runtime tests; one ordinary EventKit read was verified on the clean simulator, but actual background/foreground transitions remain open.

Day windows follow the device's civil timezone. Tests cover 5,000 days across Zurich, New York, Santiago, Kathmandu and Apia, including DST, midnight transitions and a skipped day. EventKit remains responsible for expanded occurrences. Native date controls and one ordinary local event read have simulator verification; complex events and physical devices do not.

Assistant `openCalendarAgenda` returns only a fixed `/calendar` handoff after current membership authorization. Strict native card decoding rejects injected destinations/private fields. The assistant never receives agenda event content. Partner availability UI and optional household layers are implemented; consent-bound publishing, real partner inspection and complex calendar-native smoke remain M6 work.

## Partner busy presentation

The same virtualized agenda distinguishes personal on-device details from partner busy time ranges. `assessAgendaAvailability` intersects the selected day with fresh shared coverage and preserves the uncovered remainder as unknown. No source calendar/event identity or text is inferred. An empty fresh intersection means no shared busy blocks in that coverage, never guaranteed free time. No overlap, missing snapshot, expired/future capture, or ambiguous partner identity produces unknown.

`PartnerRuntime` reads the existing authenticated API through the account lease and clears evidence on remote failure, access loss, blur/background and expiry. Its expiry timer invalidates a previously displayed snapshot without another fetch. Foreground/minute/reconnect and explicit refresh request current server evidence, so opt-out is observed on the next read; no guarantee of instantaneous remote opt-out notification is made. Shared snapshots remain in memory only. Device calendar permission is independent: partner blocks and date navigation work when personal reads are unavailable, without turning the personal failure into empty success.

Verified locally: generated clipping/coverage properties, controlled expiry, network failure/retry, canceled reads, server/local account loss, denied personal permission, and actual native HTTP/PostgREST opt-out and response-loss journeys. Real phones, APNs/realtime opt-out, AppState/network events and on-device visual/accessibility checks for partner blocks and optional layers are not verified.
